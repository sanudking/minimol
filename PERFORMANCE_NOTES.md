# MiniMoL performance release

## Optimizations

- **Zero-copy FP32 weights:** model tensors are `Float32Array` views into the SHA-256-verified partition buffer instead of being copied tensor-by-tensor. This reduces load-time work and duplicate weight memory.
- **Worker warmup:** each phone runs eight synthetic token steps while loading, then resets its KV cache. This moves initial JavaScript-engine optimization work out of the measured generation run.
- **Attention scratch reuse:** each layer reuses a 512-entry score buffer across attention heads instead of allocating a new typed array for every head and token.
- **Less UI work in the decode loop:** output rendering, progress messages, and metric updates are batched every four generated byte tokens. The model still computes and exchanges every token individually.
- **Throughput reporting:** the UI reports decode tokens/second (excluding prompt prefill) and end-to-end tokens/second (including prefill).

## Preserved invariants

- Same seed-42 FP32 partition binaries and SHA-256 fingerprints.
- Same 11,040,768-parameter, six-layer Transformer and 3+3 phone split.
- Same byte vocabulary, context limit, GELU, KV-cache behavior, and greedy argmax.
- Same direct ordered WebRTC DataChannel. No cloud inference, TURN relay, quantization, model pruning, or architecture changes.

## Verification

`node scripts/verify.mjs` passes: both partitions load and the 32-byte greedy reference fixture matches after worker warmup/reset. JavaScript syntax checks pass. The production Vite build and physical iOS/Android throughput tests still need to be run on the target environment; throughput depends on device CPU, browser, thermals, and Wi-Fi round-trip latency.

## Fair phone benchmark

1. Use the same two phones, browser versions, Wi-Fi network, and prompt for every run.
2. Set the generation length to 128 byte tokens so the short-run startup cost is less dominant.
3. Compare **decode tok/s** for steady autoregressive generation; compare **end-to-end tok/s** when prompt prefill matters.
4. Keep both tabs in the foreground, close unrelated heavy apps/tabs, and let hot phones cool before repeating a run.
5. Compare Phone 1 CPU, Phone 2 CPU, and decode throughput together. If both CPU times are low but decode throughput is low, the peer-link round trip is likely the bottleneck.

## v0.5.0 hackathon features

- Added an execution map driven by prompt, activation, and returned-token events, plus per-phone processed-position counters.
- Added a DataChannel heartbeat and rolling RTT samples; transient `disconnected` state gets a six-second recovery grace period before re-pair guidance appears.
- Added adaptive 16/8/4 KiB binary frame sizing and explicit send-queue backpressure handling.
- Added a three-run benchmark with median and best/worst decode tok/s and median end-to-end tok/s.
- Added a 32-byte distributed known-answer challenge backed by `models/reference_outputs.json`; the production postbuild now copies that fixture into `dist/models/`.
- Bumped signaling protocol to 5 and service-worker cache to v9 so both devices must use the same release and stale assets are replaced.

These are instrumentation and transport changes; the model architecture, FP32 partition files, layer split, and greedy decoding are unchanged. No physical-device benchmark has been run in this environment.
